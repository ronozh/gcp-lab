# 06 · Event-driven, config-driven orchestration (Airflow 3 on Cloud Run)

**What this phase does:** a file landing in GCS starts its feed's bronze load; an updated bronze table starts dbt; a cron rebuilds the features. No manual step. Airflow orchestrates; each DAG is a small YAML file.

## Mental model

```
EVENT    ingest/upload.sh ─▶ gs://<project>-landing/ecommerce/<feed>/<date>/<file>.csv
                               │ object finalized
                               ▼ Eventarc
         function on-file-landed: *.csv only → POST /api/v2/dags/bronze_<feed>/dagRuns
                               ▼
         Airflow 3 (Cloud Run) ─ DAG bronze_<feed> ─▶ Serverless Spark: bronze_ingest.py --feed <feed> --mode incremental
                                                                                       ▼
                                                                                 bronze.<feed>
ASSET    bronze.transaction updated ─▶ DAG gold_fct_sales: dbt build +fct_sales (silver + gold)
CRON     every 30 min 20:50–23:50 ─▶ DAG gold_sales_features: Spark gold_features.py → gold.sales_features
CONFIG   airflow/dags/*.yml ─push─▶ GitHub Action: render .py + import check ─▶ gs://<project>-airflow/dags
```

Three rules:
- **Per DAG, one run at a time.** Every DAG has `max_active_runs=1`, so a file that lands during a run queues the next run.
- **Across feeds, one Spark batch at a time.** Pool `spark` has 1 slot, because the trial's 12 vCPU quota fits one batch. Other feeds' runs start, but their task waits as `scheduled` for the slot. A batch frees its vCPUs ~1 min after it ends, so the next task holds the slot and waits until the quota reads 0 before it submits. Its log shows `waiting: vCPU quota still in use`.
- **A missed event loses nothing.** An incremental run loads *every* file not yet in bronze. If Airflow is down when a file lands, the next run picks the file up. That's why the function has no retries.

## GCP vs AWS

| GCP | AWS ≈ | Here |
|---|---|---|
| **Cloud Run service** | ECS Fargate service / App Runner | Runs the Airflow container. Manual scaling: 1 instance = up, 0 = down |
| **Cloud Run function** | Lambda | `on-file-landed`, Python. It's a Cloud Run service that Cloud Build builds from source |
| **Eventarc trigger** | S3 event notification → Lambda (EventBridge) | GCS "object finalized" in the landing bucket → the function |
| **Cloud SQL** (Postgres) | RDS | Airflow metadata DB. The smallest tier; stopped when down |
| **Secret Manager** | Secrets Manager | DB connection URL → env var in the container |
| **Cloud Storage volume mount** | EFS / Mountpoint for S3 | The `-airflow` bucket appears as a folder; DAGs are read from it (as Composer does) |
| Airflow on Cloud Run | MWAA | Same Airflow, with no always-on bill (MWAA / Composer ≈ USD 300–500/mo) |

## Infra (all Terraform, applied by CI)

| File | What | Why |
|---|---|---|
| `airflow.tf` | Bucket `<project>-airflow` | DAG files (`dags/`), mounted read-only into the container |
| `airflow.tf` | Cloud SQL `airflow-<suffix>` (Postgres 17, `db-f1-micro`) + DB + user | Metadata: runs, task states, pools. The suffix exists because a deleted name stays reserved ~1 week |
| `airflow.tf` | Secret `airflow-db-url` | The connection URL, password generated by Terraform |
| `airflow.tf` | SA `airflow` | Spark: `dataproc.editor`, `compute.viewer` (reads the vCPU quota), act as `spark-runner`. dbt: `jobUser`, `datacatalog.viewer` (policy tags), bronze viewer + lake bucket read, silver/gold `dataOwner` (tables + row policies), `connectionAdmin` on `lake`. Own: `cloudsql.client`, read the DAG bucket and the DB secret |
| `airflow.tf` | Cloud Run `airflow` | Image `apache/airflow:3.3.2`, 2 vCPU / 4 GiB, always-on CPU |
| `trigger.tf` | Function `on-file-landed` + Eventarc trigger | GCS event → Airflow REST API |
| `trigger.tf` | SAs `file-trigger`, `function-builder` | Runs and invokes the function (`run.invoker` on Airflow); builds it |

**The container is stateless.** On every start it runs `airflow db migrate`, then `airflow pools set spark 1 …`, then `airflow standalone`. Standalone runs the api-server (UI + REST), scheduler, dag-processor and triggerer with LocalExecutor. A brand-new stack (empty DB) is ready on its first start. **Recreate = re-run CI**, then deploy the DAGs again (see *Recreate*). Run history goes with the DB.

**Access is by IAM only. There's no username or password.** Cloud Run allows only identities with `run.invoker` (you as owner, and `file-trigger`). Airflow's own login is off: everyone who gets past IAM is admin. Callers send the Google token in `X-Serverless-Authorization`, which Cloud Run checks; Airflow ignores it. A browser can't send that token, so the `https://airflow-….run.app` URL returns 403. Use the proxy (`scripts/airflow.sh ui`), a local tunnel to the cloud service (≈ an SSM port-forward). Airflow still runs in the cloud.

## Config-driven DAGs

```
airflow/
  dags/<dag_id>.yml          one file per DAG; DAG id = file name
  templates/_base.py.j2      what every DAG shares: schedule, max_active_runs=1, retries
  templates/_spark.py.j2     the Spark batch helper (pool, quota wait, lab Spark settings)
  templates/<type>.py.j2     one per DAG type, extends _base
  render.py                  YAML → build/dags/*.py (+ --check: import every DAG)
```

| YAML key | Meaning | Default |
|---|---|---|
| `type` | `bronze_ingest`, `dbt_build` or `spark_job` | required |
| `description` | shown in the UI | required |
| `cron: [...]` | run on these crons, **Sydney time** | none |
| `after: <layer.table>` | run when that table is updated (an Airflow **Asset**) | none |
| neither | run only when triggered: by the event function or by hand | |
| `retries`, `retry_delay_minutes` | per task | 3, 10 |
| *(always)* | `max_active_runs=1`: one run at a time, later runs wait in the queue | |

| Type | Own keys | Runs |
|---|---|---|
| `bronze_ingest` | `feed` | Spark `bronze_ingest.py --feed … --mode {incremental, full_refresh}`. Marks `bronze.<feed>` as updated |
| `dbt_build` | `select` | `dbt build --select …` inside the Airflow container (BigQuery does the work) |
| `spark_job` | `entry`, `args` | Spark `spark/<entry>`; `${PROJECT}` in args becomes the project id |

The 6 DAGs:

| DAG | Type | Trigger |
|---|---|---|
| `bronze_<feed>` × 4 | bronze_ingest | a `.csv` lands (event), or by hand |
| `gold_fct_sales` | dbt_build `+fct_sales` (silver + gold + tests) | `after: bronze.transaction` |
| `gold_sales_features` | spark_job `gold_features.py` (overwrites) | `cron: ["50 20 * * *", "20,50 21-23 * * *"]` = every 30 min, 20:50–23:50 |

```yaml
type: dbt_build
description: dbt build +fct_sales (silver + gold) after bronze.transaction is updated
select: +fct_sales
after: bronze.transaction
```
- **Assets ≈ data-aware scheduling.** The bronze task declares `outlets=[Asset("bronze.transaction")]`. When it succeeds, Airflow starts every DAG with `after: bronze.transaction`. It fires even when the run found `nothing to do`; dbt is idempotent, so that's harmless.
- **dbt in the cloud.** CI syncs `dbt/` to `gs://<project>-airflow/dbt`. The first dbt task in a new container installs dbt into its own venv (~10 s), apart from Airflow's packages. It runs as the `airflow` SA, which is in the `all_rows` row policy so tests see every row.
- **Rendered in CI, never edited.** The `.py` files are build output (gitignored). Each one starts with `# GENERATED … do not edit`.
- **Checked before deploy.** CI renders and imports every DAG inside the **same Airflow image** the server runs. A bad YAML (unknown key, missing key, `cron` + `after` together) or a DAG that won't import stops the workflow before it touches GCP.
- **Deploy = mirror.** `gcloud storage rsync --delete-unmatched-destination-objects` copies the files: delete a YAML and its DAG disappears. Airflow picks up changes within ~30 s.
- **Two kinds of template:** `[[ feed ]]` is filled at render time from the YAML. `{{ params.mode }}` stays in the file and is Airflow's own template, filled at run time.

## How to use

**Once:** CI needs extra roles for Cloud Run, Cloud SQL, functions and Eventarc. Re-run bootstrap (idempotent), and install the proxy component the UI uses:
```bash
bootstrap/bootstrap.sh
```
```bash
gcloud components install cloud-run-proxy
```

**Start / stop** (≈ USD 0.2/h while up, from the trial credit):
```bash
scripts/airflow.sh up
```
```bash
scripts/airflow.sh down
```
```bash
scripts/airflow.sh status
```
`up` starts Cloud SQL, then one container, and waits until the scheduler is healthy (~2–3 min). `down` stops both. Files that land while Airflow is down load on the next run of their DAG.

**Open the UI** (a local tunnel that adds your Google identity; Ctrl-C stops it):
```bash
scripts/airflow.sh ui
```
Open http://localhost:8090 → **Dags**: `bronze_campaign`, `bronze_customer`, `bronze_product`, `bronze_transaction`.

**Event-driven: upload a file:**
```bash
ingest/upload.sh 2026-01-09
```
Each `.csv` starts one run of its feed's DAG. One Spark batch runs at a time, ~3 min each, plus ~1 min between batches while the quota frees up. In the UI, open a run → **Conf** shows `{"file": "gs://…csv"}`, the file that triggered it.

**Manual run, including full refresh.** In the UI: DAG → **Trigger** → `mode` dropdown → `full_refresh`. Or from the terminal:
```bash
scripts/airflow.sh run transaction full_refresh
```

**Add a DAG or a cron schedule.** Add or edit `airflow/dags/<dag_id>.yml` and push. To preview locally (needs Docker):
```bash
scripts/airflow-render.sh
```
Writes `airflow/build/dags/*.py` and prints `ok: N DAGs import cleanly`.

## Tested
| Action | Seen |
|---|---|
| Upload transaction day 9 | `bronze_transaction` run 1 **running** |
| Upload transaction day 10 during run 1 | run 2 **queued** (`max_active_runs=1`) |
| Upload customer day 9 | `bronze_customer` run **running**, task **scheduled** (waiting for the pool slot) |
| End | All succeed. Run 1 loaded days 9 *and* 10: day 10 landed before its Spark listed the files, so run 2 found `nothing to do` |
| `airflow.sh run transaction full_refresh` + `customer full_refresh` | Both tables replaced (`_meta_load_mode = full_refresh`). Customer waited 47 s for the quota, then ran on try 1 |

| Bronze transaction run → asset | `gold_fct_sales` started by itself (`asset_triggered__…`); dbt PASS=18 in the cloud |
| Cron 20:50 | `gold_sales_features` ran, sharing the Spark slot with bronze (one waited `scheduled`) |
| dbt failed (missing permission) | Retried after 10 min (`retry_delay_minutes`), then passed |

## Verify
- **Function:** Console → **Cloud Run** → `on-file-landed` → **Logs** shows `triggered bronze_<feed> run …` for each `.csv`, and `skip …` for each `.ctrl`.
- **Airflow:** a run's task log ends with the Dataproc batch `bronze-<feed>-…` succeeding. That batch is in Console → **Dataproc → Serverless → Batches**.
- **Data:** `SELECT MAX(_meta_business_date) FROM bronze.<feed>` shows the new day.

## Recreate
Everything is code. If something is deleted (or you delete it to prove the point):
```bash
gh workflow run terraform.yml
```
```bash
gh workflow run airflow-dags.yml
```
Terraform recreates whatever is missing: SQL, secret, Cloud Run, function. The container then rebuilds the empty DB and pool on start, and the second workflow redeploys the DAGs.
- A recreated stack starts **up**, billing until `scripts/airflow.sh down`.
- Run `scripts/airflow.sh up` first if Airflow is down: Terraform and a restarting container both need Cloud SQL running.

## Gotchas
- **Cloud Run, not GKE:** GKE nodes are Compute Engine VMs, so they count against the same 12 vCPU trial quota that one Spark batch needs. Cloud Run has its own quota. The same image runs on GKE (Airflow Helm chart) once the quota allows it.
- **One container, all components:** fine for a lab. For production, split the api-server (autoscaled) from the scheduler, dag-processor and triggerer, and use KubernetesExecutor or CeleryExecutor.
- **Terraform doesn't own up/down.** It ignores the instance count and the SQL activation policy, so a CI apply never restarts or stops Airflow behind your back.
- **The first event after the trigger is created can get HTTP 403** (Eventarc → function): IAM takes a few minutes to propagate, and Pub/Sub keeps redelivering, so the event still arrives. Errors from the function → Airflow call aren't retried; the function only logs a WARNING, and the next run catches up.
- **Port 8080** is often taken locally, so the UI uses 8090.
- **A new cron DAG runs its latest past slot once** on first deploy (`scheduled__<yesterday 23:50>`), then follows the schedule.
- **dbt's Iceberg tables need `bigquery.connections.delegate`** on the `lake` connection, which only `connectionAdmin` has (not `connectionUser`).
- **Starting Cloud SQL can take ~10 min** (the micro tier); `stop` takes ~1 min. `airflow.sh up` waits as long as it needs.
- **Don't save Connections or Variables in the UI.** The container is stateless and makes a new encryption (Fernet) key on each start, so saved secrets become unreadable after `down`/`up`. Configure through env vars in `airflow.tf` instead.
- **Dataproc batch ids** must be unique; the template adds the run's microseconds and the try number. Spark settings are duplicated in `scripts/run-spark.sh` and the template: change both.
