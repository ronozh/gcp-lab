# 06 · Event-driven, config-driven orchestration (Airflow 3 on Cloud Run)

**What this phase does:** a file landing in GCS starts its feed's bronze load, with no manual step. Airflow orchestrates; each DAG is a small YAML file.

## Mental model

```
EVENT    ingest/upload.sh ─▶ gs://<project>-landing/ecommerce/<feed>/<date>/<file>.csv
                               │ object finalized
                               ▼ Eventarc
         function on-file-landed: *.csv only → POST /api/v2/dags/bronze_<feed>/dagRuns
                               ▼
         Airflow 3 (Cloud Run) ─ DAG bronze_<feed> ─▶ Serverless Spark: bronze_ingest.py --feed <feed> --mode incremental
                                                                                       ▼
                                                                                 bronze.<feed>
CONFIG   airflow/dags/bronze_<feed>.yml ─push─▶ GitHub Action: render .py + import check ─▶ gs://<project>-airflow/dags
```

Three rules:
- **Per feed, one run at a time.** Each DAG has `max_active_runs=1`, so a file that lands during a run queues the next run.
- **Across feeds, one Spark batch at a time.** Pool `spark` has 1 slot, because the trial's 12 vCPU quota fits one batch. Other feeds wait for the slot.
- **A missed event loses nothing.** An incremental run loads *every* file not yet in bronze. If Airflow is down when a file lands, the next run picks the file up. That's why the function has no retries.

## GCP vs AWS

| GCP | AWS ≈ | Here |
|---|---|---|
| **Cloud Run service** | ECS Fargate service / App Runner | Runs the Airflow container. Manual scaling: 1 instance = up, 0 = down |
| **Cloud Run function** | Lambda | `on-file-landed`, Python. It's a Cloud Run service that Cloud Build builds from source |
| **Eventarc trigger** | S3 event notification → Lambda (EventBridge) | GCS "object finalized" in the landing bucket → the function |
| **Cloud SQL** (Postgres) | RDS | Airflow metadata DB. The smallest tier; stopped when down |
| **Secret Manager** | Secrets Manager | DB connection URL → env var in the container |
| **Cloud Storage volume mount** | EFS / Mountpoint for S3 | The `-airflow` bucket appears as a folder; DAGs are read from it (as Composer does) |
| Airflow on Cloud Run | MWAA | Same Airflow, with no always-on bill (MWAA / Composer ≈ USD 300–500/mo) |

## Infra (all Terraform, applied by CI)

| File | What | Why |
|---|---|---|
| `airflow.tf` | Bucket `<project>-airflow` | DAG files (`dags/`), mounted read-only into the container |
| `airflow.tf` | Cloud SQL `airflow` (Postgres 17, `db-f1-micro`) + DB + user | Metadata: runs, task states, pools |
| `airflow.tf` | Secret `airflow-db-url` | The connection URL, password generated by Terraform |
| `airflow.tf` | SA `airflow` | `dataproc.editor`, `cloudsql.client`, act as `spark-runner`, read the DAG bucket |
| `airflow.tf` | Cloud Run `airflow` | Image `apache/airflow:3.3.2`, 2 vCPU / 4 GiB, always-on CPU |
| `trigger.tf` | Function `on-file-landed` + Eventarc trigger | GCS event → Airflow REST API |
| `trigger.tf` | SAs `file-trigger`, `function-builder` | Runs and invokes the function (`run.invoker` on Airflow); builds it |

**The container is stateless.** On every start it runs `airflow db migrate`, then `airflow pools set spark 1 …`, then `airflow standalone`. Standalone runs the api-server (UI + REST), scheduler, dag-processor and triggerer with LocalExecutor. A brand-new stack (empty DB) is ready on its first start. **Recreate = re-run CI**, then deploy the DAGs again (see *Recreate*). Run history goes with the DB.

**Access is by IAM only.** Cloud Run allows only identities with `run.invoker` (you as owner, and `file-trigger`). Airflow's own login is off: everyone who gets past IAM is admin. Callers send the Google token in `X-Serverless-Authorization`, which Cloud Run checks; Airflow ignores it.

## Config-driven DAGs

```
airflow/
  dags/bronze_<feed>.yml           the DAG: one file each; DAG id = file name
  templates/bronze_ingest.py.j2    Python template for type: bronze_ingest
  render.py                        YAML → build/dags/*.py (+ --check: import every DAG)
```
```yaml
type: bronze_ingest              # which template
description: Load new transaction files from landing into bronze.transaction
feed: transaction
schedule: null                   # event only; "0 2 * * *" adds a cron timer
```
- **Rendered in CI, never edited.** The `.py` files are build output (gitignored). Each one starts with `# GENERATED … do not edit`.
- **Checked before deploy.** CI renders and imports every DAG inside the **same Airflow image** the server runs. A bad YAML or a DAG that won't import stops the workflow before it touches GCP.
- **Deploy = mirror.** `gcloud storage rsync --delete-unmatched-destination-objects` copies the files: delete a YAML and its DAG disappears. Airflow picks up changes within ~30 s.
- **Two kinds of template:** `[[ feed ]]` is filled at render time from the YAML. `{{ params.mode }}` stays in the file and is Airflow's own template, filled at run time.

## How to use

**Start / stop** (≈ USD 0.2/h while up, from the trial credit):
```bash
scripts/airflow.sh up
```
```bash
scripts/airflow.sh down
```
```bash
scripts/airflow.sh status
```
`up` starts Cloud SQL, then one container, and waits until the scheduler is healthy (~2–3 min). `down` stops both. Files that land while Airflow is down load on the next run of their DAG.

**Open the UI** (a local proxy that adds your Google identity; Ctrl-C stops it):
```bash
scripts/airflow.sh ui
```
Open http://localhost:8080 → **Dags**: `bronze_campaign`, `bronze_customer`, `bronze_product`, `bronze_transaction`.

**Event-driven: upload a file:**
```bash
ingest/upload.sh 2026-01-09
```
Four files land, so 4 runs start (one per feed). One Spark batch runs at a time and the others wait for the `spark` pool slot, ~3 min each. In the UI, open a run → **Conf** shows `{"file": "gs://…csv"}`, the file that triggered it.

**Manual run, including full refresh.** In the UI: DAG → **Trigger** → `mode` dropdown → `full_refresh`. Or from the terminal:
```bash
scripts/airflow.sh run transaction full_refresh
```

**Add a DAG or a cron schedule.** Add or edit `airflow/dags/<dag_id>.yml` and push. To preview locally (needs Docker):
```bash
scripts/airflow-render.sh
```
Writes `airflow/build/dags/*.py` and prints `ok: N DAGs import cleanly`.

## Verify
- **Function:** Console → **Cloud Run** → `on-file-landed` → **Logs** shows `triggered bronze_<feed> run …` for each `.csv`, and `skip …` for each `.ctrl`.
- **Airflow:** a run's task log ends with the Dataproc batch `bronze-<feed>-…` succeeding. That batch is in Console → **Dataproc → Serverless → Batches**.
- **Data:** `SELECT MAX(_meta_business_date) FROM bronze.<feed>` shows the new day.

## Recreate
Everything is code. If something is deleted (or you delete it to prove the point):
```bash
gh workflow run terraform.yml
```
```bash
gh workflow run airflow-dags.yml
```
Terraform recreates whatever is missing: SQL, secret, Cloud Run, function. The container then rebuilds the empty DB and pool on start, and the second workflow redeploys the DAGs.

## Gotchas
- **Cloud Run, not GKE:** GKE nodes are Compute Engine VMs, so they count against the same 12 vCPU trial quota that one Spark batch needs. Cloud Run has its own quota. The same image runs on GKE (Airflow Helm chart) once the quota allows it.
- **One container, all components:** fine for a lab. For production, split the api-server (autoscaled) from the scheduler, dag-processor and triggerer, and use KubernetesExecutor or CeleryExecutor.
- **Terraform doesn't own up/down.** It ignores the instance count and the SQL activation policy, so a CI apply never restarts or stops Airflow behind your back.
- **Dataproc batch ids** must be unique; the template adds the run's microseconds and the try number. Spark settings are duplicated in `scripts/run-spark.sh` and the template: change both.
